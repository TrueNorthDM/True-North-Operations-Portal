Overview

Everything runs on one server, in two copies: staging, where every change lands first, and production, the portal the team uses. The team reaches both through Cloudflare, and Claude looks after the server over SSH. The gold path is the path of a change: pushed to staging, then promoted to production.

Monday also tells the portal when a board changes, through the webhooks on the AAAF and HFA boards.

Publishing a change

Every change goes through Claude, lands on the staging copy first and reaches the team only when it is promoted. A developer does this:

  1. Open the Claude app, Code tab, in the TN Op Portal project.

  2. Describe the change. For a large, visible change, Claude shows how it will look first and asks before publishing.

  3. Claude changes the code and runs the checks: the type check and about 900 automated tests.

  4. Claude saves the change (commit) and sends it to GitHub (push), always on the main branch. It is the only branch.

  5. GitHub runs "Deploy to staging": in about 5 minutes the change is on staging.truenorthportal.online, a copy of the portal with a copy of the data and a yellow strip on every page.

  6. Try the change on staging. Anything done there stays there.

  7. To publish, tell Claude to promote it, or in the Actions tab open "Promote to production", click Run workflow and enter the commit tested on staging. About 5 minutes later it is live. If the new version does not answer, the server goes back to the previous one on its own.

Database changes (migrations) are applied by Claude on the server: on staging first, then on production when the change is promoted.

Rolling back: ask Claude. Or, in the Actions tab, open "Promote to production", click Run workflow and enter the code (sha) of an earlier commit.

Fresh data on staging: staging's data is a copy of production's. Ask Claude to refresh it whenever it should match today's production.

Staging is safe to break. It has its own database and sign-in. The emails the portal sends from staging go only to the owner, it runs no scheduled syncs and Monday sends it no webhooks. Sign-in codes requested on staging do arrive, from "True North Operations Portal (staging)".

Using it

  • Try a change: open staging in a private window after Claude says the change is on staging, and use the portal as the team would.
  • Publish it: tell Claude to promote it, or use "Promote to production" in the GitHub Actions tab.
  • Fresh data: ask Claude to refresh staging. It copies last night's backup, or a backup taken on the spot, into staging. Production is only read.
  • Something on staging looks wrong: don't promote. Tell Claude what you saw; the fix lands on staging again first.

Checking everything is fine

Nobody needs to look at anything every day. If something goes wrong, an alert email goes to the portal owner. No email means everything is working.

The server watch cannot send an alert if the whole server goes down. That is why the Uptime check looks from outside. Staging is not watched: the alerts are about production only.

Where to look

  • In the portal: Admin, Automations shows every scheduled job and webhook, with its last check.
  • On GitHub: the Actions tab shows the deploys and the hourly checks.
  • In Resend: the Logs screen shows every email sent. Use it to see whether someone's sign-in code went out.

The backups live in /home/tnportal/portal-backups on the server. That folder is part of ScalaHosting's own daily backup, so every night is also kept off the server.

Staging has no backups of its own: its data is a copy of production's, refreshed on request.

Restoring: ask Claude and say which day. The procedure is in deploy/README.md, Backups section.

The code does not depend on these backups: it lives on GitHub with its whole history. The COE tools have a frozen copy from October 6 in TrueNorthDM-Archive.

Only people an admin invited can sign in to the portal, always with their GoodNews email, and everyone uses 2FA. On GitHub, only people the owner invites to TrueNorthDM get in, and each sees only the repositories opened to them.

Sign-in rules: a 6-digit code by email, then the code from the authenticator app. A session lasts up to 2 months, or 15 days without use. People signing in for the first time have 7 days to set up 2FA; people who already had an account have until October 13.

On GitHub

  • Invite: in People, click Invite member, use the email or username and choose Member, never Owner.
  • Open a repository to someone: in the repository, Settings, Collaborators and teams, Add people. Read only sees the code; Write can send code.
  • Remove access: in People, click the person, then Remove from organization. It cuts everything at once.
  • Never share the truenorthdigitalmarketing login. That account owns everything.

On staging, people and invitations are those of production at the last refresh. Inviting someone or resetting 2FA on staging changes only staging.

The organization is already locked down: new members see nothing until a repository is opened to them, they cannot create or copy repositories, and GitHub 2FA is required.

Running the portal locally

Since October 5, the portal no longer runs on a developer's Mac (npm run dev): the local settings pointed at the old Supabase, which was deleted. Nothing live is affected, and the tests and deploys keep working. Staging now covers most of what running locally was for: every change can be tried there before the team sees it. A local copy is only worth it for quick experiments that should not even reach staging.

OptionWhat it isRisk
Local copy (recommended)A Supabase on the Mac with last night's copy of the data. Needs Docker DesktopNone: nothing done there reaches the real portal
Point at the serverThe portal on the Mac uses the server's databaseHigh: every click writes to the team's real data

To set up the local copy, ask Claude: "set up the local environment with a copy of the data".

Glossary

Branch
A line of work in the code. The portal uses only main.
Commit
A change saved to the code's history, with a date and a description.
Container
An isolated box on the server that runs one program: the portal, the database, sign-in.
Cron
A job the server runs on its own at a set time.
Deploy
Putting a new version of the portal live.
DNS
The directory that says which server an address leads to. Ours is at Cloudflare.
Docker
The program that runs the containers.
Migration
A change to the database's structure.
Organization
The company's space on GitHub, with members and permissions.
Production
The portal the team uses, at truenorthportal.online.
Promote
Putting a version that was tried on staging onto production.
Proxy
The doorman that receives visitors to the address and hands them to the portal.
Pull request
A request to merge a branch into main, reviewed first.
Push
Sending the commits made on the Mac to GitHub.
Repository
A project's folder on GitHub, with its whole history.
SSH
The secure way into the server from the command line.
Staging
The test copy of the portal, at staging.truenorthportal.online, with a copy of the data.
Supabase
The set of services that gives the portal its database, sign-in and files. It runs inside our server.
Token
A password for programs, giving access to a service.
VPS
A server rented just for us. Ours is at ScalaHosting.
Webhook
An automatic notice a service sends the portal when something changes. Monday does this.
2FA
The second step of signing in: the code from the authenticator app on your phone.
